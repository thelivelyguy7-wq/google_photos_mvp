# PHASE-BY-PHASE ARCHITECTURE — GOOGLE PHOTOS AI-NATIVE RETRIEVAL MVP

This architecture document maps the technical implementation directly to the user's retrieval journey defined in the problem statement.

---

## Precondition Phase: Storage & Indexing (Available)
*The intended photo must exist and be searchable.*

- **Media Storage (Object Store):** Stores the raw image files.
- **Metadata Index (Relational / NoSQL):** Indexes deterministic, exact attributes (e.g., Exif data, GPS coordinates, timestamps, explicitly tagged faces).
- **Semantic Vector Database:** Stores multi-dimensional embeddings of images generated by a Vision-Language Model (e.g., CLIP, Gemini Vision). This enables matching vague concepts (e.g., "beach café vibe") rather than exact keywords.

---

## Phase 1: Remember (User Cognitive State)
*The user knows a specific photo exists but lacks precise identifiers. They hold a contextual, rich mental image.*

- **Technical Translation:** None. This phase happens entirely in the user's mind. The system's goal is to minimize the friction between this mental state and the client interface in the next phase.

---

## Phase 2: Express (Context Extraction)
*The user describes what they remember naturally. The AI interprets this into structured retrieval clues.*

- **Input Component:** A unified, natural language UI component in the client (React/Vite).
- **Context Interpretation Engine (LLM):** 
  - **Function:** Parses the unstructured text (e.g., "Goa trip beach café sunset with my cousin" or "Kerala houseboat with family").
  - **Output Pipeline:** Breaks the query into two parallel query streams:
    1. **Hard Filters (Deterministic):** Extracts known entities (People: `[Cousin, Family]`, Location: `[Goa, Kerala]`, Time: `[Sunset/Evening]`).
    2. **Semantic Vectors (Probabilistic):** Converts the descriptive vibe ("beach café", "houseboat") into text embeddings.
- **Session State Initialization:** The system creates a new Retrieval Session ID, storing the original query and the extracted context in a state manager.

---

## Phase 3: Discover (Contextual Candidate Retrieval)
*The system converts clues into retrieval signals and presents plausible candidates.*

- **Hybrid Retrieval Service:** 
  - **Action:** Executes a concurrent search against the underlying databases.
  - **Vector Search (KNN/ANN):** Queries the Vector Database using the Semantic Vectors to find visually/conceptually similar images.
  - **Metadata Intersection:** Filters the vector search results through the Metadata Index using the Hard Filters (e.g., bounding results to Goa).
- **Ranking Engine:** Scores the resulting candidates based on confidence intervals. Images satisfying both semantic similarity and metadata constraints rank highest.
- **Candidate Set Generation:** Returns a capped list (e.g., Top 20) of plausible candidates back to the client.

---

## Phase 4: Narrow (Recognition Layer)
*When multiple plausible photos appear, the user reviews and narrows the set using contextual filters.*

- **UI Rendering:** The client displays the Candidate Set in a responsive image grid.
- **Dynamic Contextual Filters:** 
  - **Function:** The backend analyzes the metadata distribution *of the specific returned Candidate Set* (e.g., noticing half the photos are from 2022 and half from 2023).
  - **Output:** Surfaces dynamic refinement chips (People | Place | Date | Activity) to the UI, allowing the user to trim the candidate set without typing.
- **Human-in-the-Loop:** The system defers the final judgment to the user. No AI is applied to force a single "correct" answer here.
- **Session State Update:** The system records which photos were shown and which filters the user interacted with.

---

## Phase 5: Recover (Guided Recovery)
*If the user rejects the candidates ("None of these"), the system suggests the next useful path based on existing clues.*

- **Failure Trigger:** User clicks a "Not what I'm looking for" action.
- **Recovery Analysis Engine (LLM / Heuristics):**
  - **Function:** Consults the Session State Manager to analyze the failed attempt.
  - **Evaluation:** Evaluates the confidence scores of the initial context extraction. (e.g., "The location 'Goa' or 'Kerala' was a high confidence extraction, but 'Cousin' was fuzzy.")
- **Guided Next Steps Generation:**
  - Suggests logical pivots rather than dropping the user at a blank search bar.
  - *Pivot Types:* Broaden (drop a constraint), Narrow (add a constraint), Shift (try a related location/time).
- **Iterative Loop:** The user selects a recovery suggestion, the Session State is updated with the new parameters, and the system loops back directly to **Phase 3: Discover** without losing prior context.

---

## Architectural Constraint: LLM Optimization & Cost Efficiency
*To prevent excessive latency and cost, the architecture strictly isolates LLM invocation from the core retrieval loop.*

1. **The "Gatekeeper" Pattern (Phase 2 Only):** The LLM is invoked exactly *once* per journey to translate the unstructured query into a structured payload (`{ hardFilters, semanticVibe }`).
2. **Deterministic Retrieval (Phase 3):** The actual image search uses fast, cheap Vector Search (ANN/KNN) and boolean SQL/NoSQL intersections. We **do not** feed candidate images or metadata rows into an LLM for evaluation.
3. **Client-Side Filtering (Phase 4):** Faceted filtering (Dates, Locations) is generated dynamically via simple array mapping in the frontend/backend. Zero AI is used for filtering.
4. **Bypassing the LLM on Pivot (Phase 5):** When a user triggers a recovery pivot (e.g., "Broaden to everywhere"), the system mutates the existing JSON state locally and directly hits the Phase 3 Vector/Metadata database again. **It does not re-prompt the LLM.**

---

## Summary of AI Allocation by Phase

| Phase | Core Capability | AI / Tech Required |
| :--- | :--- | :--- |
| **1. Remember** | Mental visualization | *Human Cognition* |
| **2. Express** | Unstructured memory to structured signals | **LLM (NLP / Entity Extraction)** |
| **3. Discover** | Candidate retrieval and ranking | **Hybrid Search (Vector Embeddings + Metadata)** |
| **4. Narrow** | Candidate inspection and dynamic filtering | *Metadata Distribution Logic & Human Judgment* |
| **5. Recover** | Suggesting intelligent pivots from failure | **LLM (State Analysis) / Rules Engine** |
